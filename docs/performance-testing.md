# 性能测试方案

本文说明如何为 CT 调度平台建立可重复的性能测试、夹具和分层门禁。方案覆盖前端、后端、数据格式迁移、文件访问、分析和调度结果回放；具体阈值见 [性能标准](performance-standards.md)。

## 测试夹具

测试夹具必须由确定性的生成器创建，使用固定随机种子，并在清单中记录 `schemaVersion`、设备数、测试数、文件数、总字节数、Route 数、轮次、晶圆数、Move 数、预期规范化哈希和预期迁移结果。夹具是测试输入，不是生产主数据副本。

必须覆盖以下场景：

| 场景 | 目的与规模要求 |
| --- | --- |
| `small` | 日常开发冒烟；约 3 台设备、30 个测试、约 5 MB。 |
| `medium` | 接近当前实际规模；单设备约 150–250 个测试、约 50 MB。设备总数仍不得超过 10 台。 |
| `deep` | 单设备约 1000 个测试，发现全测试扫描和索引退化。 |
| `wide` | 目录宽度测试；最多 10 台设备，每台少量测试，发现设备级扫描。 |
| `large-test` | 单个测试包含大量轮次、CJob、PJob 和 Route 配置，验证单测试读写。 |
| `migration` | 覆盖每个已发布历史 `schemaVersion`，包含正常、边界、冲突、损坏和中断恢复夹具。 |
| `moves` | 1 万、5 万、10 万条 MoveList，验证分析、响应体积、内存和前端回放。 |
| `concurrent` | 保存测试、读取概览和四路批量排程并发，验证锁等待、数据一致性和尾延迟。设备总数不超过 10 台。 |

## 必测链路

### 后端与存储

- 启动：未迁移、需要迁移、已完成迁移且数据未更新三种状态；验证 HTTP 监听顺序和重复启动成本。
- `/api/health`、设备列表、设备概览：验证响应时延、响应大小以及不读取完整 `test.json`。
- 单个测试读取和保存：验证只访问目标测试，且未修改测试哈希不变。
- 单测试与测试组删除：在其他指标完成后依次删除一个测试和夹具中的完整测试组，以单次端到端最大耗时分别执行门禁。
- 单测运行准备：验证 `/api/run` 只读取设备概览和目标测试，并限制收到请求到首次算法 `init` 的附加耗时。
- Route 保存和改名：分别验证无全量扫描，以及只更新真实引用者。
- 导入导出：验证包校验、版本拒绝、同 ID 冲突拒绝、恢复备份和大包进度。
- 分析与结果：覆盖大 MoveList、已保存结果引用、Baseline 和 HongYe/MoveList 输出校验。

### 迁移

每个历史版本必须执行：规范化等价性、幂等重复执行、原子切换、备份恢复、中断恢复、高版本拒绝和索引一致性测试。迁移测试必须同时测冷启动耗时、CPU、峰值内存、临时目录大小和文件访问数量。

### 前端

在真实浏览器中测量“点击—请求—JSON 解析—渲染—可交互”各阶段，至少覆盖设备列表、概览、单测试切换、保存、时间轴回放和大 MoveList。记录主线程长任务、帧间隔、网络响应体积和前端资源体积；前端不得自行承担后端分析或持久化职责。

## 访问计数与可观测性

测试运行时应记录：文件读取/写入次数、读取/写入总字节数、JSON 解析次数、迁移阶段、文件锁等待、序列化时间、算法时间、输出校验时间和响应写出时间。HTTP 可使用 `Server-Timing` 暴露分段，浏览器使用 Performance API 记录交互阶段，但日志不得包含业务数据内容。

结构性断言优先于时间断言。例如设备列表读取测试应直接断言读取的路径集合不包含 `tests/*/test.json`；单测试保存应断言其他测试的读取、写入和哈希均未变化。

## 执行分层

### PR 门禁（目标 3–5 分钟）

运行结构性文件访问红线、`small`/`medium` API 测试、一个历史迁移夹具、核心正确性回归和基本前端构建检查。任何正确性或文件访问失败立即阻断；延迟预算使用性能标准中的 P95 试运行值。

### 夜间回归

运行 `deep`、`wide`、`large-test`、`moves`、`concurrent` 和完整历史迁移矩阵，生成 JSON 与 HTML 报告。夜间结果用于识别趋势，并对超过相对回归规则的结果创建待处理项。

### 发布门禁

在固定 Windows 机器上运行全量套件，并与上一正式版本比较。环境必须固定 CPU/内存配置、Windows 版本、电源模式、Python/Node 版本、依赖锁文件、浏览器版本和后台进程策略。发布门禁必须通过性能预算、相对回归规则、正确性红线和数据访问硬门禁。

PSE300 真实批量门禁在固定性能机设置
`CT_RUN_PSE300_BATCH_PERFORMANCE=1` 后运行
`tests/performance/test_pse300_batch_performance.py`。它使用“公司单腔示例集-130”、
平台校验、跳过 Baseline 和生产四进程路径，完整墙钟必须不超过 260 秒。

## 基准与报告

基准报告至少包含：提交号、基准版本、运行时间、固定机器配置、夹具清单、设备数、测试数、文件数、总字节数、P50/P95/P99、峰值内存、响应体积、文件访问计数和失败原因。报告应保留历史结果以绘制趋势，但不得把被 `.gitignore` 排除的真实运行数据提交到仓库。

建议统一提供本地和 CI 入口，例如性能夹具生成命令与性能套件运行命令；命令应支持只运行指定场景、输出机器可读 JSON、设置基准版本和复现失败样本。任何数据格式或 `schemaVersion` 变更都必须自动选择完整迁移性能矩阵。

当前统一入口如下；脚本使用 `CT_DATA_DIR` 启动隔离服务，不会访问生产数据：

```powershell
python -m pytest tests/performance/test_storage_performance_contracts.py -q
python scripts/run_performance_suite.py --profile small --enforce
python scripts/run_performance_suite.py --profile medium --migration --enforce
python scripts/run_performance_suite.py --profile medium --baseline previous.json --enforce
python scripts/run_performance_suite.py --profile concurrent --enforce
python scripts/run_performance_suite.py --profile moves --enforce
```

规模定义位于 `performance/profiles.json`，试运行预算位于
`performance/budgets.json`。默认报告写入 `output/performance-report.json`；该目录
不进入版本控制。服务响应携带 `Server-Timing` 和 `X-Response-Bytes`，报告还记录
Python、平台、夹具哈希、响应体积和服务进程峰值常驻内存。

## 变更触发矩阵

| 变更类型 | 强制测试 |
| --- | --- |
| 数据格式、迁移器、索引 | 全部迁移正确性、启动、设备列表、概览、单测试读写删除、测试组删除、导入导出和访问计数。 |
| 后端存储/API | 文件访问数量、接口时延、响应大小、锁等待、并发和 `medium`/`deep`。 |
| 前端 | 构建检查、浏览器交互时延、主线程长任务、资源体积和大 MoveList 回放。 |
| 调度算法 | Validation、Makespan、算法 CPU 分位数、超时率、内存和结果一致性。 |
| 分析模块 | 大 MoveList 分析时延、内存、响应体积和摘要一致性。 |
| 发布版本 | 全量性能套件、历史迁移矩阵及固定 Windows 机器对比。 |

## 实施顺序

先实现启动、设备列表、设备概览、单测试读取/保存/删除、测试组删除和历史迁移链路的结构性访问测试；再生成 `medium`/`deep` 夹具，修复全目录读取和全文件时间戳扫描；随后加入 HTTP、内存和响应体积测试，最后接入浏览器交互、夜间回归和发布门禁。完成一周基线后冻结性能标准中的绝对预算。
