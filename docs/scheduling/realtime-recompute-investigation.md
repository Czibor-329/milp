# 实时重算性能退化调研与修复

## 结论

R2 与 R2-refer 当前不是等价对照：

- R2 是两个 CJob，每批 6 片；第二批分别在 100/200/300/400 秒到达，并从 LP2 进入。
- R2-refer 是一个 CJob，12 片在 0 秒全部可见，并全部从 LP1 进入。
- R2 内还混用了 Heuristic、RL、Neural 以及 `petri-look`、`joint` LoadLock 管理器。

因此不能要求两组 makespan 完全相等。一次性参考拥有未来到货信息，也改变了 CJob 边界、
LoadPort 和运行策略。正确验收应固定策略与 LoadLock 管理器，并让参考保留两个 CJob、
6+6 片及 LP1/LP2，只把两批都提前暴露给调度器；若还要隔离在线信息差，应为第二批加入
与 R2 相同的 release time。

代码中同时存在真实的重算退化，现已修复：

1. 新批次的 PM 分配只看切点瞬时占用，没有统计旧批次的剩余工序。旧片已离开 PM、
   但未来还要回到该 PM 时会被漏算，导致 3 个等价 PM 上出现 1/3/2 的静态分配。
2. 重算启发式只有“先整批排空 WIP”一种偏好。该策略稳定但会破坏流水；另一方面，
   完全放开新旧片并行并非所有状态都更好。
3. 同 Route 的普通 CJob 拆单被发片负载比例当成不同产品族，Job 边界会不必要地改变
   派工顺序。

修复后，PM 按残余加工工时分配新增片；重算同时评估“保守排空”和“新旧并行”两条
可行轨迹，以 makespan 选优，同目标时优先保守轨迹；自适应轨迹按 Route 而不是 CJob
统计发片比例。Petri 可达性、驻留约束和精确定时仍是两条轨迹共同的安全层。

## 研究依据

制造业动态调度通常采用 predictive-reactive / rolling-horizon 框架。研究并不假设
“重算天然不损失性能”，而是同时处理：

- 效率：makespan、cycle time、tardiness 或吞吐。
- 稳定性：相对已发布计划的动作、顺序或完成时刻偏移。
- 在线信息边界：新订单到达前不可用于首排，因此必须用 release time 公平比较。
- 冻结或 match-up：保留正在执行及近期承诺的动作，只在有限窗口内重排，并尽快回到
  原计划状态。

相关工作：

- Ouelhadj、Petrovic，动态制造调度综述：
  <https://doi.org/10.1007/s10951-008-0090-8>
- Vieira、Herrmann、Lin，重调度策略、触发政策与方法框架：
  <https://doi.org/10.1023/A:1022235519958>
- Aktürk、Görgülü，match-up scheduling：
  <https://doi.org/10.1016/S0377-2217(97)00396-2>
- Lim 等，带 wafer transfer delay 的 cluster-tool 实时调度：
  <https://doi.org/10.1080/00207543.2013.808774>
- Zhou，cluster tool 离线周期调度与实时控制的两层架构：
  <https://doi.org/10.3182/20090610-3-IT-4004.00003>

本次采用的是轻量 predictive-reactive portfolio：已经启动的动作与必要收尾继续冻结，
其余残差问题同时生成稳定候选和自适应候选。它比直接增加一个稳定性罚项更适合当前
Heuristic + Timing 架构，也不需要改变 MoveList 接口。

## 后续验收建议

前端测试组建议拆为三个口径：

1. `静态合批`：一个 CJob、12 片、0 秒到达，用于测静态吞吐上限。
2. `静态拆单`：两个同优 CJob、6+6 片、0 秒同时可见、LP1/LP2，用于测 Job 边界不变性。
3. `在线到货`：第二个 CJob 在 100/200/300/400 秒才可见，用于测真实重算性能。

在线到货应主要对比带相同 release time 的离线 oracle，同时报告：

- 最终 makespan 与 oracle gap；
- 已发布旧动作的顺序/开始时间偏移；
- PM 工作量离散度；
- 重算 CPU 时间和冻结动作数量。
