# 性能标准

本文规定 CT 调度平台后端、前端、数据存储和调度结果处理的性能基线、硬性门禁及例外处理方式。它与 [数据格式说明](data-format.md) 和 [平台架构](architecture.md) 配套使用，适用于开发、合并、夜间回归和发布验收。

## 适用范围与规模边界

- 一个工作区的设备数最多为 **10 台**。任何夹具、压测或性能报告不得以超过 10 台设备作为正常业务规模；需要测试目录宽度时，使用 10 台设备的 `wide` 场景。
- `realtime_scheduler/data/datasets/` 是设备和测试集的唯一主数据来源。性能测试不得创建第二份生产数据镜像，也不得将运行时缓存作为基线数据。
- 设备、测试集和结果应使用稳定 UUID；性能指标必须同时记录业务规模和数据字节数，避免只报告一个与数据量无关的耗时。
- 启动时必须先完成数据迁移和重复模板清理，再创建 HTTP 监听器；迁移期间页面不得读取半迁移数据。

## 指标分类

所有性能报告至少包含以下四类指标：

1. **端到端时延**：从请求发出到响应完整可用；使用 P50、P95，必要时记录 P99。
2. **资源使用**：峰值内存、CPU 时间、响应体大小和前端资源体积。
3. **数据访问复杂度**：读取/写入文件数量、读取/写入总字节数、是否解析完整测试文件。该类是结构性硬指标，不因机器快而放宽。
4. **正确性与可恢复性**：迁移前后规范化数据哈希、文件哈希、索引一致性、幂等性和备份可恢复性。

算法 CPU Time 只能作为算法指标，不能替代 API 总耗时、文件访问成本或浏览器交互时延。

## 数据访问硬门禁

以下规则默认适用于正常交互路径。违反任一规则即阻断合并，除非变更说明明确列出受影响的数据规模、原因和替代方案，并由维护者批准。

| 操作 | 硬性要求 |
| --- | --- |
| 列出设备 | 不读取或解析任何 `tests/*/test.json`；只读取设备元数据或测试摘要索引。 |
| 打开设备概览 | 不读取完整测试内容；允许读取设备文件、共享配置和测试摘要索引。 |
| 读取单个测试 | 只读取目标测试及其必要引用；不得因为一次读取扫描或解析全部测试。 |
| 保存单个测试 | 不读取、解析或改写其他测试；仅更新目标测试及必要索引。 |
| 删除单个测试 | 只更新摘要索引并删除目标目录；不得读取、改写或回传其他完整测试。 |
| 删除测试组 | 通过组清单和摘要索引定位成员；不得为定位成员解析完整测试。 |
| 保存未改名的 Route | 不扫描全部测试，除非调用方明确要求引用分析。 |
| Route 改名 | 可遍历受影响测试，但只改写真正引用该 Route 的文件，并报告访问数量。 |
| 普通启动（格式版本未变化且数据未更新） | 不重复解析完整测试，不重复执行全量迁移。 |
| 迁移 | 必须逐版本迁移、先写临时目录、校验成功后原子启用，并保留可恢复备份。 |

测试通过文件访问计数器或等价的可观测接口验证上述规则，不能只依赖耗时断言。

## 用户体验试运行预算

以下是第一版试运行预算。冻结前应在固定 Windows 机器收集至少一周基线；冻结后按 P95 执行，P50 用于发现趋势。

| 场景 | P95 预算 |
| --- | ---: |
| 无迁移冷启动至 HTTP 可用 | ≤ 3 秒 |
| v5→v6 `medium` 数据启动迁移 | ≤ 20 秒 |
| 热请求 `/api/health` | ≤ 300 毫秒 |
| 设备列表 | ≤ 200 毫秒 |
| 最大规模设备概览 | ≤ 300 毫秒 |
| 读取单个约 200 KB 测试 | ≤ 150 毫秒 |
| 删除单个测试 | ≤ 300 毫秒（单次最大耗时） |
| 删除一个测试组及其测试 | ≤ 300 毫秒（单次最大耗时） |
| 单测运行准备（不含算法与输出校验） | ≤ 300 毫秒 |
| 平台状态推进（1000 个 Move，P95） | ≤ 500 毫秒 |
| 130 项批量测试（单项算法 ≤ 2 秒） | ≤ 260 秒 |
| 保存单个测试 | ≤ 300 毫秒 |
| 普通 Route 保存 | ≤ 300 毫秒 |
| 四路常用 API 并发读取 | ≤ 1 秒 |
| 1 万 / 5 万 / 10 万条 MoveList 分析 | ≤ 1 / 5 / 10 秒 |
| 切换测试至页面可编辑 | ≤ 500 毫秒 |
| 首次打开至主要控件可交互 | ≤ 2 秒 |
| 时间轴播放帧间隔 | ≤ 25 毫秒（目标约 50 FPS） |
| 单次前端主线程长任务 | ≤ 50 毫秒 |

整设备导入导出、批量 Route 改名、大 MoveList 分析和数据迁移必须使用独立预算，不得套用普通交互预算。长任务必须提供可见进度、可取消性或明确的完成状态；页面不得读取未完成迁移的数据。

单测运行准备从服务端收到 `/api/run` 请求起，统计到首次算法 `init` 边界；
这段只允许读取设备概览和目标测试，不得加载同设备的其他完整测试。前端状态栏仍统计
点击到结果可用的完整耗时，算法轮次耗时与输出校验耗时应作为独立阶段展示和诊断。

批量测试默认使用四个、最多使用三十个相互隔离的算法进程，避免内置算法的全局会话锁把
worker 退化为串行执行。HongYe 校验使用独立的 1~15 路共享并发配额，自动补算的
Heuristic Baseline 与所选策略必须共同受该配额约束，不能让 MoveStateSim 数量跟随算法
worker 数增长。8 项及以上启用进程隔离，小组继续使用线程以免支付进程冷启动；
页面批量状态最多每秒轮询一次，并且仅在项目状态变化时重绘测试卡片。
批量结果卡片必须按测试名称自然数字顺序排列且不得按完成时间重排；结果区域应限制高度并内部
滚动，避免 130 项卡片持续拉长页面。测试选择只向服务端发送选中的稳定测试 ID，
服务端仍以工作区顺序过滤，不能信任调用方顺序。

## 相对回归规则

性能比较必须在同一固定环境、同一夹具、同一启动方式下与基准版本比较：

- P50 退化超过 15%，且绝对增加超过 30 毫秒：阻断。
- P95 退化超过 20%，且绝对增加超过 50 毫秒：阻断。
- 峰值内存或响应体积增加超过 10%：当前试运行门禁直接阻断；积累一周固定机器数据后，可将 10%~20% 调整为必须说明、超过 20% 阻断。
- 正常交互路径的文件读取数或写入数增加：默认阻断，即使总耗时未超预算。
- 只有一次异常样本不得直接判定回归；应重跑并记录样本数、分位数和环境信息。稳定失败仍按门禁处理。

## 正确性红线

性能优化、数据格式变更和迁移实现均必须保持：

- 迁移前后规范化语义一致，设备、Route、Clean、组别、测试和 Baseline 不丢失；
- 迁移可重复执行，第二次执行不再改变结果；
- 迁移中断后可由备份恢复；高于当前支持版本的数据必须拒绝；
- 同 ID 不同内容的导入不得静默覆盖；
- 测试索引与实际测试文件一致；
- 未修改测试的内容哈希和文件哈希保持不变；
- 调度结果仍通过 MoveList/HongYe 校验。

任何正确性失败优先于性能指标，直接阻断合并或发布。

## 报告与例外

每次报告必须带有提交号、基准版本、操作系统版本、Python/Node 版本、CPU/内存、夹具名称、设备数、测试数、文件数、总字节数，以及 P50/P95、峰值内存和文件访问计数。

临时超预算必须提交书面例外，注明原因、影响范围、恢复期限和后续任务；例外不得豁免数据访问硬门禁或正确性红线。默认例外有效期为一个发布周期。
